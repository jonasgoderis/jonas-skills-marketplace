How the session grader works

A walkthrough of the rubric, the grades and the pipeline behind /evaluate-session, written for someone meeting rubrics for the first time.

1 · The whole idea in one picture

This is an “LLM-as-judge” setup: a model (Haiku) grades something against written rules. It helps to picture a teacher marking an exam:

📄
The exam paperThe digest: a small JSON summary of one session
📋
The marking schemeThe rubric plus the catalogue of 19 practices
🧑‍🏫
The teacherThe grader: Haiku, given the prompt, rubric and digest
🅰️
The markThe scorecard: a band (A+ to D) and up to 2 focus items
The thing being graded is how you drove the session: your prompts, how you scoped the work, how you checked it. It does not grade the code or the assistant's answers. A session that shipped working code after six vague prompts should grade badly. A carefully scoped session for work that turned out to be unnecessary should grade well.

Two kinds of “eval” live in this repo

3 · The catalogue: 19 practices, and how visible each is

references/best-practices.md defines BP-01 to BP-19. Each has an observability label, which tells the grader whether a transcript can show the practice at all. You need this to understand the rest of the page.

Direct: visible in your messages Indirect: only from specific signals Structural: a fact about the project's files None: happens outside the transcript
BP-01Watch the context, hand off before it rots
BP-02Split project context across files
BP-03Break big tasks into small, checkable steps
BP-04One session, one subject
BP-05Checkpoint knowledge to disk
BP-06Be specific: goal, constraints, audience
BP-07Show a concrete example
BP-08Spell out the format
BP-09Iterate; first answer is a draft
BP-10Do not inject the answer
BP-11Zoom out first, zoom in on request
BP-12Keep the main thread clean
BP-13Offload deterministic work to scripts
BP-14Reference files, loaded on demand
BP-15Verify; confident ≠ correct
BP-16Read the actual diff
BP-17Keep a human deciding real consequences
BP-18Mind what you share
BP-19Keep rules in separate files

BP-18 is labelled Direct, but it can only show up as a failure: a session that leaked a secret never reaches the grader, because the secret gate stops it first.

4 · Four buckets: where each practice ends up

Each of the 19 practices lands in exactly one bucket on the scorecard. Seeing all 19 lets you check that the grade didn't depend on something the grader couldn't see.

Focus on

It went wrong and it cost something. Two at most.

Did well

There is positive evidence you did it. “Nothing went wrong” doesn't count.

Not applicable

The session gave no chance to use it (e.g. no big irreversible decision came up).

Unobserved

The digest has no signal for it. This is not held against you.

How the grader decides, per practice

Is it structural (BP-02, 14, 19)? Decide from the project's files. It can only be Did well, or a one-line Standing note, never a focus item.files, not you
Did the session give any occasion to use it?no → Not applicable
Does the digest carry any signal for it?no → Unobserved
Did its failure happen, costing something you can quote from your own message?yes → Focus candidate
Is there positive evidence you did it on purpose?yes → Did well
The fairness rules. Because the digest removes the assistant's words, your messages are the only text left to “blame”. The rubric works against that:
  • Every finding cites a practice and a message number. “Prompts were vague” doesn't count as a finding. “BP-06, message 4” does.
  • Rework is not automatically your fault. It counts against you only if the missing information was yours to give and the grader can say what you should have written.
  • Anything the assistant chose (a design, a tool, a file layout) is never a finding against you.

5 · From evidence to a grade: the bands

The grade doesn't count how many practices you ticked. It counts costs. A cost is an episode the grader can point to where you had to repeat yourself, correct a misunderstanding your own wording caused, or ask for a redo that a clearer instruction would have avoided.

Try it: a band calculator
A+
A+
No costs and at least two practices clearly used on purpose. Should be rare.
A
No costs, or one so small the session absorbed it without a detour.
B
One or two costs.
C
Three or four costs, or one that redirected the whole session.
D
Five or more, or the session never established what it was doing.

Why only five bands? A judge choosing between 11 grades won't give the same answer twice on the same evidence. A coarse grade that stays the same from run to run is more useful than a precise one that jumps around. Tie-break: if the evidence fits two neighbouring bands, the grader picks the higher one. A harsh grade gets ignored, and that costs more than a generous one.

6 · Anatomy of a scorecard

①# Session scorecard — demo-project, 2026-09-23 ②**Grade: C** ③Five costs traceable to the user's own wording; unclear scope set off most of them. ## Focus on ④- **BP-06 — Be specific** — message 3 relied on a convention that was never stated, and the rate-limiter work was undone. - **BP-10 — Do not inject the answer** — message 6 declared a cache problem; message 7 retracted it after a detour. ## Did well ⑤BP-02, BP-19 ## Not applicable ⑥BP-07, BP-08, BP-17, … ## Unobserved BP-12, BP-13, BP-16, … ⑦<!-- session: 1a2b… -->
  1. Header: project and date.
  2. Band, A+ to D, decided by counting costs.
  3. One sentence saying what shaped the grade most.
  4. At most two focus items: the two biggest costs, each on a different episode, each citing a message number. One or zero is fine.
  5. Did well: identifiers only, no commentary. This is recognition, not a second essay.
  6. Not applicable / Unobserved: listed so you can see what the grade didn't rest on.
  7. A hidden session ID, so a tool can link the scorecard back to the transcript.

Illustrative example based on the synthetic “bad” calibration session, not a real one.

7 · Grading the grader: calibration

The rubric pushes toward generous grades, and a lot of practices can be “unobserved”. Together those create a risk: everything quietly lands at A, and the tool stops measuring anything. Real sessions can't catch this, because a run of A grades from someone who already works well looks the same whether the rubric works or not.

The fix is a negative control: a session built to go badly, with known faults. If the grader can't mark that down, it's broken. make-sessions.py generates two synthetic sessions in the same healthy project, so the only difference between them is how the work was asked for:

“bad” session: messagePlanted cost
3Relies on a convention that was never stated, so the rate-limiter work gets undone
5A reversal that throws away the CSV export just finished
7The diagnosis you injected at message 6 (“definitely caching”) was wrong
10Approved at message 9 without looking at what was approved
14An instruction ambiguous enough to be read the other way

Rule of thumb: editing rubric.md, best-practices.md or grader-prompt.md makes these numbers stale. Rerun plugin/evals/session-calibration/calibrate.sh. It exits non-zero if “bad” grades B or better.

Glossary

Rubric
The written rules for turning evidence into a grade. Here: references/rubric.md.
Catalogue
The list of practices being assessed (BP-01 to BP-19): references/best-practices.md.
Grader / judge
The model that applies the rubric. Here: Haiku, via claude -p.
Band
A coarse grade (A+, A, B, C, D). Coarse on purpose, so it stays the same from run to run.
Cost
An episode you can point to where your wording led to a repeat, a correction or a redo.
Digest
The small JSON evidence file: your messages verbatim, everything else reduced to counts.
Observability
Whether a transcript can show a practice at all: direct, indirect, structural or none.
Calibration
Checking the grader against sessions whose right answer you already know.
Negative control
A deliberately bad case. If the grader passes it, the grader is broken.
