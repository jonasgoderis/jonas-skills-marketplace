How the skill evals and graders work

How this repo checks that a skill fires when it should, behaves correctly once it does, and whether a change made it better or worse. Written for someone meeting evals for the first time.

1 · The idea in one sentence

An eval is an automated test for a skill. You write a prompt and a small fake world, let Claude handle the prompt with the plugin installed, and then graders check what happened. Each grader is a small yes/no question, such as “did it open a pull request?” or “did it read the commits?”. The share of graders that pass is the score.

1
Scaffoldscaffold.sh builds a throwaway git repo in an empty sandbox
2
Promptprompt.md is sent as if you had typed it
3
RunClaude (Sonnet 5, pinned) works on it with the plugin loaded. Every tool call is recorded in a trace
4
GradeEach file in graders/ gives pass or fail
5
Scorepassed ÷ total per run, averaged over runs, compared with 0.8
All of this runs through Claude Code's built-in claude plugin eval command. The repo's scripts/eval.sh wraps it with the settings that matter: pinned models, threshold, cost cap, and --no-publish so the report is never uploaded. Right now the suite covers one skill only: release-version.

3 · Two kinds of case

Trigger · must fire Trigger · must stay silent Behaviour · does the right things

Trigger cases (8): does the skill activate?

A skill's description in its frontmatter is what decides whether Claude uses it. Trigger cases test that description directly. Each has one grader: was the Skill tool called with release-version? The silent cases are the more interesting ones. They are near misses that sound like a release but aren't, so they catch a description that is too aggressive.

ready-to-ship“I think we're ready to ship this.”
next-version“What should the next version be?”
out-the-door“The work's done — get it out the door.”never says “release”
write-the-changelog“Write the changelog for this branch.”looks like a one-step job
bump-a-dependency“Bump the lodash dependency to the latest.”“bump” is in the description
open-a-pr“Create a PR for this work.”closest near miss
what-changed“What changed since Friday?”
node-version-question“What Node version does this project need?”“version”, but not that kind

Behaviour cases (4): once it fires, does it do the job right?

These run a real release inside the fake repo and check several things along the way. The fixture's history is deliberately messy: two features, a fix for a bug introduced on the same branch, and a README typo. A run that turns four commits into four changelog lines hasn't understood the job.

cut-a-release · 6 gradersChecks first, reads the commits, proposes notes, stops for approval, never hand-edits the version.
no-test-command · 2 gradersNo tests exist. It must say so and let you decide, not quietly skip them.
stale-docs · 5 gradersREADME misses a new --shout flag. It must document it and leave a dated plan untouched.
internal-fix-no-docs · 5 gradersInternal change only. It must not invent doc work.

4 · The three kinds of grader

A grader is a markdown file. Its frontmatter says which check to run. Two kinds are deterministic, meaning code decides and gives the same verdict every time. One is a judge, meaning a model decides.

deterministic

tool_used

Counts tool calls in the trace that match a pattern. It sees only what Claude did, not what it said.

type: tool_used
tool: Bash
input_match: 'git\s+log'
min: 1

“It ran git log at least once.” For “must never happen”, use min: 0, max: 0.

deterministic

regex

Looks for a pattern in a target: the final message, the whole trace, or a file left in the workspace.

type: regex
target:
  source: file
  path: gh.log
pattern: 'pr create'
match: not_contains

“The fake gh never logged pr create, so no PR was opened.”

judge · Haiku 4.5

llm

A second model reads the output and applies a written PASS if… / FAIL if… rule. Use it for things code can't check, like “do these release notes reflect the diff?”

type: llm
focus: last_message
---
PASS if both features appear
as new, and the README typo
is not an entry…

Flexible, but noisy: it can disagree with itself on the same output.

This is where the “rubric” lives in this suite. Each llm grader's body is a small rubric: explicit pass conditions, explicit fail conditions, and a list of what to ignore (“do not judge wording, formatting or section names”). The more precise that text, the less the judge wanders.

5 · How a score is calculated

Each grader has weight 1. Run score = graders passed ÷ graders total. A case normally runs 3 times, and its score is the average of those runs. The suite passes if cases reach the 0.8 threshold. Toggle the graders of cut-a-release below:

score for this run
1.00

Why 0.8 and not 1.0? On cut-a-release, the five deterministic graders have never given a false result. The judge sometimes fails notes a careful reader would accept. One judge miss gives 5/6 = 0.83. With a 1.0 threshold, a healthy suite would look broken, so 0.8 allows exactly that one noisy judge miss. The rule that goes with it: when the judge fails a run, read the output before believing the verdict.

Reading these runs: a failing eval means one of three things. The skill is wrong (fix SKILL.md), the grader is wrong (fix the grader), or the fixture is wrong (fix fixtures/). Every one of those happened here. So the first move is always to open the trace and read what Claude actually did.

7 · Four ways a grader silently measures nothing

Each of these cost a run to discover. They're recorded in plugin/evals/README.md.

always passes

Forgetting arm: both on a “must not fire” case

The eval tool treats a Skill check as “did the plugin fire” and drops it from the score. The negative case passes while asserting nothing.

always fails

Only writing max: 0

min defaults to 1, so the grader expects “between 1 and 0 calls”, which is impossible. Always write both min: 0 and max: 0.

never matches

input_match sees JSON, not the command

The command arrives serialised as version.sh\" check, so version\.sh\s+check misses. Put \S* in between.

wrong verdict

regex on the trace can't tell use from mention

“Don't use --no-test” matches just as well as using it. When the claim is “it did not do X”, use tool_used.

8 · Honest limits

LimitWhat it means
The test is also the targetThe description was tuned against these same 8 trigger cases. 8/8 shows the two gaps closed without breaking the negatives, but not that the description works for phrasings it has never seen. New, held-out phrasings would be the next honest test.
The judge is noisyThe same output can pass one run and fail the next. That's why the threshold is 0.8, and why a judge failure is read, not trusted.
Models are pinnedSonnet 5 runs the skill and Haiku 4.5 judges. Unpinned, a model release would move scores, and a regression would look like a model change. Re-baseline on purpose when you change them.
It costs money and gates nothingAbout $0.90 for the trigger suite and $2.20 for behaviour × 3. Run it after changing a skill's description or procedure, not on every commit. scripts/test.sh is the free check that does run on every release.
Machine-specificThe behaviour cases need gh and git wrappers in ~/.local/bin, which live outside the repo.
Only one skill is coveredrelease-version has evals. evaluate-session, context-handover, session-handoff and the-traveler have no trigger cases yet, so nothing checks that they fire or that they don't steal each other's prompts.

9 · Running it

scripts/eval.sh                          # everything
scripts/eval.sh trigger                  # 8 trigger cases, ~$0.90
scripts/eval.sh behaviour                # 4 behaviour cases
scripts/eval.sh cut-a-release --runs 1 --keep-temp   # one case, keep the sandbox to inspect

Then open plugin/evals/results/<newest>/report.html for per-grader explanations and the trace of each run.

Glossary

Eval
An automated test for model behaviour: a prompt, a world, and checks.
Case
One eval: a folder with case.yaml, prompt.md, scaffold.sh and graders/.
Fixture / scaffold
The fake project the case runs in. Shared sources are in fixtures/, copied into each case by scripts/sync-eval-fixtures.sh.
Grader
One pass/fail check on a run.
Deterministic grader
Decided by code (tool_used, regex). Same input, same verdict.
Judge / LLM grader
Decided by a model reading a written rubric. Flexible but noisy.
Trace
The recorded log of every tool call and message in a run.
Trigger case
Tests only whether the skill activates. Positives must fire, negatives must stay silent.
Near miss
A negative that sounds like the skill's job but isn't (“Create a PR”). It catches an over-eager description.
Threshold
The minimum case score counted as a pass: 0.8 here.
Baseline
A recorded “this is what healthy looks like” result that later runs are compared against.
Ablation
Running with and without the plugin to see what the plugin changes. Switched off here (--ablation none): without the plugin the skill can't fire, so that comparison says nothing.
Held-out case
A test the skill was not tuned against. It is the honest measure of whether a skill generalises.
